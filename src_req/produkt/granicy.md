# Границы репозитория и продукта (WEB UI/UX)

> **Статус:** черновик на основе «Консолидированного пакета» (финальные файлы 1–7).  
> **Аудитория:** PDE, ASE, QSRE — чтобы не тащить backend в задачи UI.  
> **Сводка приоритетов P0/P1/P2** — в `prioritety.md`, не здесь.

## Назначение документа

Зафиксировать:

1. границу **репозитория AV Control WEB_UI** (только WEB UI/UX);
2. продуктовые **Out-of-Scope** и отложенные направления, влияющие на экран;
3. **разделение ответственности** между веб-поверхностями и backend-документами пакета.

## 1. Граница репозитория AV Control WEB_UI

### 1.1 В scope репозитория

| Поверхность | Содержание | Источник |
|-------------|------------|----------|
| **Admin Web UI** | Единый веб: администрирование контроллера/ПО **и** конфигуратор проекта/драйверов; единая авторизация; разделы по ролям | PSD §1.2, §1.3 |
| **Клиент комнаты** | Веб-приложение в браузере и клиент-оболочка (киоск); отображение состояния, действия пользователя; **не** прямое управление железом | PSD §1.2, §1.4; PRD M-ROOM; Logic §1.1 |
| **Сквозной WEB UX** | Тексты сообщений, вход, отражение прав на экране, offline/ошибки с точки зрения пользователя | Scope §4 (владелец текстов — UX / Data Schema); PRD NFR-UX |

Папки требований: `vozmozhnosti/konfigurator`, `klient-komnaty`, `admin-kontroller`, `obshchiy-interfejs`.

**Конфигуратор (M-PRJ) в UI:** замена Studio — настройка серверного и клиентского проектов через веб; **не настраивает сам контроллер** (сеть, время → M-ADM; SSL и пользователи → M-SEC). | PRD M-PRJ |

**Admin (M-ADM) в UI:** эксплуатация контроллера через веб: состояние, сеть, время, перезагрузка. | PRD M-ADM |

### 1.2 Вне scope репозитория (другие команды / артефакты)

Реализуют и описывают **не в этом репозитории**, даже если в пакете есть FR:

| Тема | Где в пакете | Что может быть в WEB UI |
|------|--------------|-------------------------|
| Ядро, HAL, Driver Runtime, Scenario Engine | PSD §1.2; Core & API | Только отображение статуса, ошибок, wizard-шаги |
| Контракты REST/WebSocket, Driver Engine (`DRV-ENG-*`), JS-контракт | Core & API; Scope: `TL-CORE-*` | Вызов через API; UI не дублирует контракт |
| Схемы данных, ER, ACM, шифрование at rest | IA & Data Schema §2.5 | Экранные формы и read-only представления |
| Физические интерфейсы, протоколы, OS/Hardware | PSD §2 | Не реализуем |
| Лицензия: криpto, provisioning, формат | PSD §2.4, §6; PRD M-LIC | Только UX статуса («UX не строится вокруг лицензии» — Scope P0) |
| Watchdog, Safe Mode, boot — **механика** | PSD §2.2.5; Core & API | Индикаторы и действия admin UI, не алгоритм |
| Числа LIM-01…LIM-11 | Scope, приложение А | Сообщения при превышении; бенчмарки — тех. лид |
| Машинные пользователи API | PRD §2 | Контракт API, не UX |

**Правило потока управления (обязательно для UI):** `Клиент → Сервер → устройства`. Клиент/панель **отображает** и **инициирует**; оборудованием **напрямую не управляет**. | Logic §1.1; PSD §1.2; ENT-15 (IA) |

**Единый источник истины:** состояние на сервере, клиент — представление. | PSD §1.1 |

## 2. Out-of-Scope продукта (Scope §2) — влияние на WEB UI/UX

Ось «в объёме (P0/P1/P2)» vs «Out-of-Scope» — Scope §0.2. Ниже — только то, что **запрещает или откладывает экран**.

### 2.1 Вне объёма навсегда (§2.1)

| ID | Что исключено | Влияние на WEB UI/UX |
|----|---------------|----------------------|
| **OOS-01** | Собственная система ВКС | Нет UI «встроенной ВКС»; интеграция через драйвер (слой C). На клиенте — команды/состояние звонка, не платформа VCS |
| **OOS-02** | Собственная система бронирования | Нет календаря платформы; потребление событий брони через драйвер |
| **OOS-03** | BMS / здание-уровень (KNX/DALI/Modbus/BACnet как BMS) | В UI — комнатные сценарии и реле/входы, не BMS-канвас |
| **OOS-04** | Универсальный low-code canvas / визуальное программирование | Нет бесконечного canvas; управляемая логика типовых помещений (PRD M-AUT) |
| **OOS-05** | Облако / SaaS | Offline-first; нет UI облачного портала, телеметрии в SaaS | PSD §1.7 |
| **OOS-06** | Прямое управление оборудованием **из клиента** | Клиент не шлёт команды в HAL; только через сервер/сценарии | PRD M-ROOM |
| **OOS-07** | «Толстый» клиент (iRidium Server driver, прямой TCP) | Не проектируем legacy-пути в UI клиента |
| **OOS-08** | Произвольная запись в теги через API; создание сценариев машинным пользователем | В UI интегратора — не «API playground» для произвольных тегов |
| **OOS-09** | Домашняя автomation USB-стик (Zigbee и т. п.) | Нет соответствующих экранов настройки |

### 2.2 Отложенные направления (§2.2)

| ID | Направление | Сейчас в UI | Влияние на WEB UI/UX |
|----|-------------|-------------|----------------------|
| **OOS-10** | Standalone / serverless-панель | Топология «Сервер + Клиенты» | Не проектируем UI под «панель = сервер+клиент» до v1.0 | PSD §1.6 |
| **OOS-11** | Production-эмулятор Windows | Эмулятор как среда проб (≈20 мин) | Полноценный эмулятор в UI — не MVP |
| **OOS-12** | Глубокая кастомизация UI (уровень i3 Pro) | Ограниченная кастомизация (FM-07 / FR-PRJ-07) | В MVP/P1 — текст, иконки, цвета, видимость, порядок блоков; **не** расширяемость i3 Pro | PRD коммент. M-PRJ |
| **OOS-13** | Форматы SIEM CEF/LEEF | syslog/SNMP/Zabbix/Prometheus/REST | В admin UI — не экраны CEF/LEEF без запроса ИБ |

## 3. Границы из PRD (комментарии к модулям)

| Модуль | Граница для UI | Источник |
|--------|----------------|----------|
| **M-PRJ** | Настройка контроллера → M-ADM; SSL/пользователи → M-SEC; форматы/хранение проекта → §2.5 PSD; **глубокая кастомизация и произвольная логика → вне MVP** | PRD M-PRJ коммент. |
| **M-ROOM** | Прямое управление из клиента исключено; legacy TCP — вне MVP; **FR-ROOM-09** (типовые состояния) настраиваются в M-PRJ, на клиенте — **рантайм** | PRD M-ROOM |
| **M-AUT** | Не визуальная платформа программирования; JS — расширение, среда исполнения в PSD | PRD M-AUT |
| **M-VAR** | Расширенные выражения (строки, массивы…) → вне MVP; в UI — связи/теги в рамках Expression Evaluator без JS | PRD M-VAR |
| **M-SEC** | IEEE 802.1X, AD/LDAP, продвинутая авторизация → после MVP; в UI — базовая аутентификация веб и отражение RBAC | PRD M-SEC |
| **M-LIC / после MVP** | Полный эмулятор Windows; serverless-панели | PRD § M-LIC коммент. |

**NFR граница:** `NFR-SCALE-03` — многообъектное централизованное управление **вне MVP** (не проектируем «единый центр всех объектов» в v1 UI). | PRD NFR |

## 4. Границы из Logic & User Flows (для экранов)

| Тема | Граница | UI-следствие |
|------|---------|--------------|
| Оператив vs проект | Изменение состава оборудования, связей, базовой логики — **правка проекта** (FL-PRJ-BUILD + deploy), не «оперативный слой» комнаты | Клиент комнаты не редактор проекта |
| JS | Нативной логики не хватает → JS (§7); JS — **расширение**, не основной путь | Конфигуратор: нативные правила первичны; редактор JS — ограниченный |
| Бронь / ВКС на панели | UI брони с панели — **P2**; API создания брони — отдельно; связывание брони — настройка интегратора | Не закладываем P2 UI брони в MVP без явного change |
| Доступ | Формальная матрица `профиль × действие × ресурс` → **ACM** | UI реализует экраны; матрица — IA & Data, не дублировать в src_req |
| Diagnostic bundle | Собирает IT/инж локально; вендор без доступа в контур | UI: кнопка/мастер выгрузки, не «облачная отправка» |

## 6. Слои интеграции (Scope §0.3) — что показываем в UI

| Слой | Смысл | UI |
|------|-------|-----|
| **B — открытый API** | Сервер отдаёт внутреннее наружу | Admin/интеграции: настройка токенов, не «управление железом через API» (согласовано с OOS-06, API-REQ-10) |
| **C — драйверы** | Сервер управляет ВКС, бронью, устройствами | Конфигуратор: установка/привязка драйверов; клиент: результат сценария, не SDK драйвера |
| **Потребляемая инфра** (NTP, AD/LDAP) | Сервер — клиент IT | Admin: NTP/сеть на экране; AD/LDAP UI — после MVP (PRD M-SEC) |

**Бронь и ВКС — драйверы, не «свой API продукта».** | Scope §0.3 |

## 8. Что не копировать в этот файл целиком

- Матрица §1 Scope (~112 FM) → `prioritety.md`.
